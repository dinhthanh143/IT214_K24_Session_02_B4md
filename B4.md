# Bài 4 — Phân tích và tái thiết kế tầng dữ liệu theo Database-per-service

## 1. Phân tích điểm Coupling ẩn (Hidden Coupling) ở tầng dữ liệu
Trong đoạn mã `getBorrowingDetail`, `borrowing-service` đang thực hiện truy vấn SQL:
```sql
SELECT b.title, m.name FROM borrowings br 
JOIN books b ON br.book_id = b.id 
JOIN members m ON br.member_id = m.id 
WHERE br.id = ?
```

**Những rủi ro và vi phạm nguyên tắc Database-per-service:**
- **Vi phạm tính đóng gói dữ liệu (Data Encapsulation):** Bảng `books` thuộc quyền sở hữu của `book-service`, và bảng `members` thuộc quản lý của `member-service`. Việc `borrowing-service` thọc tay trực tiếp bằng lệnh `JOIN` vào bảng của người khác đã phá vỡ ranh giới dữ liệu giữa các dịch vụ.
- **Rủi ro vỡ hệ thống khi thay đổi Schema (Schema Coupling):** Nếu đội ngũ phát triển `book-service` quyết định đổi tên cột `title` thành `book_name`, hay chuyển đổi bảng `books` sang dạng NoSQL, đoạn code của `borrowing-service` sẽ ngay lập tức bị lỗi (crash) vì câu lệnh SQL cứng nhắc bị sai. Đội `book-service` cũng không dám mạnh tay tái cấu trúc database vì sợ ảnh hưởng đến đội khác.
- **Rủi ro về hiệu suất:** Khi chia sẻ chung một cơ sở dữ liệu `librax_db`, một câu query JOIN nặng nề do `borrowing-service` chạy có thể ngốn hết tài nguyên CPU/RAM của database, gây ảnh hưởng đến hiệu năng của tất cả các service khác đang dùng chung DB.

## 2. Sơ đồ tái thiết kế Database-per-service
Để giải quyết bài toán trên, cơ sở dữ liệu nguyên khối `librax_db` sẽ được tách ra làm 4 database riêng biệt hoàn toàn (thậm chí có thể khác nhau cả về loại DBMS):

- **`books_db`**: Chứa bảng `books` và các dữ liệu liên quan đến ấn phẩm. **Chỉ duy nhất `book-service`** được quyền kết nối và thao tác.
- **`members_db`**: Chứa bảng `members`. **Chỉ duy nhất `member-service`** được phép kết nối.
- **`borrowings_db`**: Chứa bảng `borrowings`. Chỉ lưu trữ `book_id` và `member_id` dưới dạng ID (Foreign Key tham chiếu ảo), không được phép chứa dữ liệu trùng lặp như tên sách hay tên độc giả. **Chỉ do `borrowing-service`** thao tác.
- **`notifications_db`**: Chứa các thông tin về trạng thái gửi tin nhắn, lịch sử thông báo... thuộc thẩm quyền của `notification-service`.

*(Không một service nào được phép truy cập trực tiếp vào DB của service khác. Mọi trao đổi dữ liệu bắt buộc thông qua REST API hoặc Message Broker).*

## 3. Tái cấu trúc code `getBorrowingDetail` không dùng JOIN
Thay vì thực hiện JOIN ở tầng SQL, `borrowing-service` sẽ query thông tin cơ bản từ `borrowings_db` của mình trước, sau đó gọi REST API sang 2 service còn lại để gom dữ liệu theo mô hình **API Composition (Aggregator)**.

```java
@Service
public class BorrowingService {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @Autowired
    private RestTemplate restTemplate; // Cấu hình @LoadBalanced

    public String getBorrowingDetail(Long borrowingId) {
        // 1. Chỉ truy vấn bảng borrowings thuộc borrowings_db để lấy ID tham chiếu
        String sql = "SELECT book_id, member_id FROM borrowings WHERE id = ?";
        Map<String, Object> borrowingData = jdbcTemplate.queryForMap(sql, borrowingId);
        
        Long bookId = ((Number) borrowingData.get("book_id")).longValue();
        Long memberId = ((Number) borrowingData.get("member_id")).longValue();

        // 2. Gọi API sang book-service để lấy Title
        String bookUrl = "http://book-service/api/books/" + bookId;
        BookDto book = restTemplate.getForObject(bookUrl, BookDto.class);
        String title = (book != null) ? book.getTitle() : "Unknown Book";

        // 3. Gọi API sang member-service để lấy Name
        String memberUrl = "http://member-service/api/members/" + memberId;
        MemberDto member = restTemplate.getForObject(memberUrl, MemberDto.class);
        String name = (member != null) ? member.getName() : "Unknown Member";

        // 4. Tổng hợp dữ liệu (Aggregation) ở tầng Application
        return "Book: " + title + ", Borrowed by: " + name;
    }
}

// Các class DTO bổ trợ dùng để mapping dữ liệu trả về từ API
class BookDto {
    private String title;
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
}

class MemberDto {
    private String name;
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}
```

## 4. Bài toán mới phát sinh và Hướng xử lý sơ bộ
Khi áp dụng triệt để Database-per-service, việc phụ thuộc dữ liệu cứng bị loại bỏ, nhưng hệ thống lại phải đối mặt với các vấn đề phân tán phức tạp.

**Bài toán: Truy vấn liên kết (JOIN chéo) bị chậm / Vấn đề N+1 Query**
- *Mô tả*: Việc phải gọi giao thức mạng HTTP liên tục sang các service khác (như ví dụ lấy `title` và `name` ở trên) tốn kém tài nguyên và độ trễ mạng (Network latency) hơn hàng trăm lần so với một lệnh JOIN SQL chạy nội bộ DB. Đặc biệt, nếu hệ thống cần xuất một danh sách gồm 1000 lượt mượn sách, hệ thống phải thực hiện tới 1000 cuộc gọi API đến `book-service` và 1000 cuộc gọi API đến `member-service` (Vấn đề N+1), khiến server quá tải ngay lập tức.

- *Hướng xử lý sơ bộ*: 
   1. **Chế độ gọi Bulk/Batch API:** Yêu cầu `book-service` mở thêm một API dạng `GET /api/books?ids=1,2,3` để lấy toàn bộ dữ liệu 1000 quyển sách chỉ trong **1 vòng gọi mạng duy nhất**.
   2. **Lưu đệm (Caching):** Dữ liệu như tên sách hay tên độc giả rất ít khi thay đổi. `borrowing-service` có thể lưu các `title` và `name` này vào Redis Cache để tái sử dụng ngay từ lần query thứ hai mà không cần gọi API.
   3. **Áp dụng Pattern CQRS kết hợp Message Broker:** Để phục vụ các màn hình truy xuất (Read) báo cáo lớn, ta có thể cho `borrowing-service` lắng nghe (subscribe) các sự kiện cập nhật (`BookUpdatedEvent`) từ Kafka/RabbitMQ. Khi tên sách thay đổi, Kafka báo cho `borrowing-service` tự lưu lại bản sao của tên sách đó vào một View Database nội bộ. Khi xuất báo cáo, `borrowing-service` chỉ việc gọi JOIN trên View Database nội bộ của chính nó mà không phụ thuộc vào bất cứ ai.
